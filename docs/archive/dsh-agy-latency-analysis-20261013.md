# DSH 与原生 AGY 的真实编码耗时对照（2026-10-13）

同一编码任务实测：DSH 经代理耗时 **912.75 秒（15 分 12.75 秒）**，原生 AGY 耗时 **379.03 秒（6 分 19.03 秒）**，本次相差 **2.41 倍、533.72 秒**。两边均完成代码、测试和 README，且通过独立验收。

主要问题已经定位到三处：DSH 的 Windows 临时目录权限导致测试停滞和多轮排障；桥接会话反复追加工具配置，随后发生 AGY 原生上下文压缩及工具参数错误恢复；代理等完整结果校验后才交付，使这些等待期间没有业务输出。HTTP 网络及代理处理的直接耗时合计约 10.47 秒，不能解释数分钟的差距。

这是一次工作流对照，包含模型行为、工具环境和系统提示差异，**2.41 倍不能解释为纯代理开销或稳定性能倍数**。本轮没有修改生产代码或部署配置。

后续已将工具配置改为 AGY 会话启动时加载一次，见[重复配置修复与验收](session-tool-configuration-fix-20261013.md)。本文保留修复前的测量数据。

修复后的完整真实编码重测见[2026-10-14 报告](dsh-agy-latency-rerun-20261014.md)：DSH 851.714 秒，原生 AGY 442.024 秒；本次无重复工具配置、无压缩、无参数修复，仍复现 Windows 沙箱下的临时目录权限与单测挂起。

## 测试方法与验收

- 相同任务原文：用 Python 标准库实现 `taskbox.py`，支持任务增删、完成、状态/标签筛选、JSON 输出、单调 ID、原子持久化及损坏数据保护；编写并实际运行至少 10 项 unittest，生成 README。
- DSH 使用已经从源码安装、构建的 `deepseek-harness`，提交 `d743267388641bc76f17c45ce8b4c231aed1d32c`，版本 `0.2.1-alpha.2`。实际启动为 `pnpm dsh --profile headless --json -`，通过 stdin 完整传入任务，没有使用 npx。
- 两组都使用服务器 AGY **1.3.4**、同一托管账号、`gemini-3.8-flash-high`、`effort=high`，依次执行。DSH 使用实际生产代理，经本地只做计时的透明 HTTP relay 转发原始请求；没有改工具定义或添加桥接提示。
- DSH 工具在 Windows / Python **3.13.5** / `workspace-write` 沙箱执行。原生 AGY 在同一服务器容器的空隔离目录执行，Python **3.12.15**，使用默认 agent 和 `--mode accept-edits --dangerously-skip-permissions`。操作系统、沙箱和工具集不同，是重要的对照限制。
- DSH 客户端重试设为 0；代理允许一次恢复。本地计时使用单调时钟，服务器内部阶段使用服务器日志，未用两台机器的绝对时间差冒充网络单程延迟。

| 服务器 AGY 尝试累计 | **742.93 秒** | 包含推理、上下文压缩、CLI 初始化与内部处理，含失败候选及修复 |
| DSH 本地工具等待 | **152.96 秒** | 包含 120 秒和 15 秒两次测试停滞，文件操作、测试与诊断 |
| 主流程 HTTP 减去 AGY 尝试时间 | **10.47 秒** | 网络、解析、调度、校验、进程回收等待及交付的合计残差 |
| DSH 启动至首请求 | 4.71 秒 | 包括 pnpm/客户端启动 |

主流程 HTTP 累计 753.40 秒；响应头延迟中位数 **0.260 秒**，业务内容延迟中位数 **13.09 秒**，最长 **194.42 秒**。5 次 `/health` 探测为冷连接 0.217 秒，后续约 0.075–0.080 秒；这是 HTTP 往返观测，不是纯线路 RTT。

标题生成并行耗时 **18.55 秒**，使用相同 high 模型，但不在主流程关键路径上串行相加；它可能造成的上游并发影响未通过消融测试量化。透明 relay 请求读取到转发的准备时间见逐请求证据。

正常请求的服务器 `agy result` 到执行器完成日志中位约 **5 毫秒**。这个间隔包含校验与收尾，并非校验器的独立 CPU 耗时；修复后的进程回收有约 2.11 秒收尾，下一请求也观察到约 2 秒等待。主会话前 22 轮使用同一 AGY 进程，只有修复和修复后的正常历史重建发生新建，未发现每轮都冷启动。

## 具体问题及证据

### 1. Windows 沙箱的临时目录问题放大成了约 6.5 分钟排障

DSH 第一次跑测试从相对时间 **263.81 秒**开始，到 **651.94 秒**才首次拿到全量通过结果；这段共 **388.13 秒**，包含 **235.89 秒模型请求**和 **151.24 秒本地工具等待**。

第一次测试在 `test_done_command` 停留，120 秒后 DSH 将命令转为后台任务；后续单测复现又等待了 15 秒。诊断明确出现 `TemporaryDirectory()` 生成目录后，写入/清理报 `PermissionError / WinError 5`。工作区普通子目录内相同增删/完成操作成功。

把第一次停滞时的源码和测试复制为快照，用同一个 Python 3.13.5 在沙箱外运行，**17 项测试在 3.86 秒内完成，全部通过**。DSH 后来使用工作区内唯一临时子目录并清理，在原沙箱中 **3.46 秒**跑通 17 项测试。

这证明本轮存在本地执行环境问题，不能归因于代理网络或代码测试本身要跑两分钟。Python 3.13、临时目录权限与 DSH 沙箱的具体机制尚未做版本消融，不能据此声称已经定位到 DSH 的某一行缺陷。

### 2. 复用会话仍然重复追加工具配置，上下文膨胀后发生压缩

客户端每次声明 25 个工具。代理 `ExternalTools.prompt()` 虽然使用增量历史，但每轮仍加入完整 `[Client tool configuration]`，长度 **20,883 字符**。首个主会话 22 轮累计重复追加 **459,426 字符**工具配置；还会重放上一条 assistant 调用，以绑定代理生成的调用 ID 与结果。

对应源码为 `app/external_tools.py` 的 `context`、`prompt` 和 `run`，以及 `app/agy.py` 中 `input_offset = len(existing.client_history) - 1`。不能把客户端 HTTP 本身携带完整历史误认为服务器每轮都重放了全部历史：本次确认使用的是增量消息，重复的是工具配置和桥接指令，另有上一条 assistant 回显。

首个主会话第 21 次生成的输入上下文已到 **194,323 tokens**。下一轮有明确的 `CHECKPOINT`，内容以 `Resuming from a compaction` 开始：

这里的 194,323 是压缩前最后一次可见生成的输入规模，并非已测定的压缩阈值；下一轮还加入了新消息。这是 AGY 会话层的自动上下文压缩（compaction），不代表模型的最大上下文窗口只有约 20 万 tokens，也不足以证明 AGY 使用固定大小的滑动窗口。模型标称容量和 agent 提前整理历史的策略属于不同层级；本次未确认该模型别名在 AGY 接入端的实际硬上限、内部触发阈值或阈值配置方式。

114 秒是检查点创建到下一次普通生成开始的观测间隔，包含 AGY 压缩相关处理和等待；没有单独测量压缩模型调用的纯推理耗时。40.89 秒则是代理启动新 CLI 进行参数修复的独立尝试耗时。

压缩摘要长 11,121 字符，`file_path` 出现次数为 0，也没有完整工具配置标记。压缩后下一次普通生成输入仅 4,770 tokens，紧接着出现字段名错误。这支持“压缩后没有保留完整参数契约”的判断；严格证明压缩是字段错误的唯一原因，仍需要保留契约与不保留契约的消融对照。

这里观察的是 AGY 自身的压缩行为，上下文计量单位是 tokens；此前代理的 200,000 字符检查已经移除。本轮没有恢复或新增代理输入长度限制。

代理只恢复一次，修复成功。无效 `read` 没有交付给 DSH，实际交付的是有效的 `todo_write` 和 `write`。本次没有重现 `num_turns` 不匹配故障，也没有恢复循环。

### 3. high 推理和整轮缓冲共同造成长时间无业务输出

另一个长请求耗时 **164.32 秒**，其中 AGY 自身为 **164.06 秒**。这是一次普通生成，无修复，CLI 报告 output 23,951 tokens，其中 reasoning **20,021 tokens**，最终提交实现文件的写入请求。

共享执行器 `app/execution.py` 在拿到完整 CLI `result` 并校验后才交付内容与工具；因此响应头和心跳很快到达，但客户端在上述 164 秒、194 秒期间拿不到业务内容。缓冲本身没有额外制造等长推理时间，但会隐藏中途进展，放大“什么都没发生”的感受。本次没有记录代理背后真实模型首 token 时间，不能把 HTTP TTFB、心跳、`first_business` 或 `first_delta` 当成它。

原生 AGY 首工具约 15.27 秒出现，最长普通模型生成约 **69.09 秒**，最终回答的首个 `text_delta` 在约 370.32 秒出现。原生也不是立即输出最终答案；区别是它在任务过程中直接提供并执行原生工具进展。

本次两边都用了 high，所以不能单凭输出量证明 high 设置错误。DSH 路径的额外诊断、提示结构、压缩和恢复都改变了模型工作量；精确分摊这些因素需要后续消融测试。

### 4. skills 没有出现协议适配失败

DSH 成功加载 `create-readme` 和 `diagnose-windows-sandbox-acl`。它们会带来额外内容和往返，但本次参数恢复错误发生在普通 `read` 工具；没有证据支持“skills 的参数适配坏了”。沙箱诊断 skill 被加载是因为本地测试发生权限问题。

## 建议的优化顺序

1. **先解决测试环境停滞**：固定目标 Python 版本，单独复现 DSH 沙箱与临时目录行为，让实际命令的退出/超时/权限错误及时暴露。不要通过无限加大模型超时来掩盖工具挂起。
2. **减少桥接上下文重复，并保证压缩后契约仍然完整**：不再每轮将同一大段工具配置追加到历史；同时将工具契约放在压缩后仍可靠可用的位置，或在压缩后显式恢复。必须保留调用 ID 配对及完整校验，先在隔离实例测试，不直接改生产行为。
3. **增加可见阶段计时**：至少区分排队/初始化、AGY 运行、压缩、修复、本地工具与交付。若调整流式策略，需要另行验证无效工具调用不会提前泄漏；心跳不能伪装成模型输出。
4. **随后再做性能消融**：同一操作系统、固定 Python、消除临时目录故障，对比配置只传一次/当前模式，以及 high/其他 effort，跑多个样本。标题模型可单独测量后再决定是否降低 effort。
