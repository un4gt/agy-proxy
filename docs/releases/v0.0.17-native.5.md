# v0.0.17-native.5 — 轮次校验与模型目录

2026-10-22。已完成本地、独立容器及正式服务验证，并更新日本节点。

## 故障与根因

Pi 会话 `01a15f47-9bbf-7081-98e0-b6b45982dcad` 使用 `test` Key，实际模型为
`gemini-3.8-flash-high`。故障发生时正式服务运行 `native.3`。

三次请求分别耗时约 14.0、50.1、66.3 秒。第二次请求缺少 `finish`，由代理按既有预算恢复一次后成功。
第三次请求 `agy_3b5824a85b4745b09a8a288207d64dcb` 在新的 CLI 会话中报
`CLI turn number mismatch`，请求记录为 `ERROR 502`，没有触发 600 秒总超时。

持久化 CLI 轨迹显示：第一次模型响应没有调用工具；CLI 随后自行插入一条要求继续并调用 `finish`
的用户输入，第二次模型响应才调用 `finish`。因此一次客户端请求对应两个 CLI `user_input` 步骤。
旧代码把 CLI 的累计 `num_turns` 与客户端请求次数直接比较，在内容校验前拒绝了结果。
原始 stdout 未保留；证据来自会话记录、服务端请求日志及只读查询的 CLI 轨迹。

详细时间线仅在本地保留；测试与发布结果见下文。

## 修复

- 共享轮次计数器按唯一 `user_input.step_index` 计数，重复 ACTIVE/DONE 更新只计一次。
  CLI 内部提醒计入 CLI 轮次，客户端请求计数仍独立保留。原生和常规后端使用相同规则。
- 额外轮次必须有输入步骤佐证；仍拒绝计数倒退、无依据跳跃、错误类型、已完成步骤重放及跨会话事件。
- 修复两条 FIFO 的到达顺序：CLI 结果先到时，等待内部提醒对应的后续请求及结构化提交捕获，
  再执行已有的 `finish`、内容一致性和请求完成校验。
- CLI 已结束后，捕获通道最多继续排空 5 秒，并受原总截止时间限制；不完整时报告
  `native_capture_incomplete`，不再占用剩余的模型生成超时。轮次异常报告 `native_turn_invalid`。
- 日志补充 CLI 累计轮次及 CLI 结果耗时。保持一次代理恢复预算、模型思考档位、工具权限及校验后交付规则。
- 两个 Dockerfile 均包含共享计数模块；常规镜像同时补齐输入保护模块。

## 验证与边界

- 合并模型目录修复后，Windows 全套：663 passed、2 skipped，跳过项要求 Linux PTY。
- 最终镜像内 Linux 全套：665 passed，无跳过。测试挂载补齐开发用导出脚本；修正模拟 CLI 测试对镜像原生后端开关的继承，以及输入审计环境变量的隔离。
- 覆盖内部提醒后继续复用、累计用量差分、重复步骤、异常计数、跨会话步骤、两种 FIFO 到达顺序及捕获丢失后的有界失败。
- 最终镜像内，固定 CLI 1.4.0 / GDB / 输入清理开启的真实两轮验证通过，复用同一会话，分别约 9.0、3.5 秒。
- 通过提示诱发内部提醒的真实探针未复现该分支，模型直接提交了 `finish`；该分支目前由持久化故障轨迹和确定性事件回归覆盖。
- `test` Key 保留的 396 条请求中没有 504 或 `upstream_timeout`；18 条超过 120 秒，最长约 267 秒。
  这些历史记录包含验证请求，不能据此推断日常延迟分布。当前用户确认的问题是 ERROR 502。
